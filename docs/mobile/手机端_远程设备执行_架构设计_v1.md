# 无为手机端 · 远程设备执行（Claude Code 订阅 + 多电脑切换）架构设计 v1

> 需求来源（2026-10-02 董事长）：
> ③ 手机端能直接用「电脑端已登录的 Claude Code 订阅版」——不只走无为托管币。
> ④ 多电脑端切换——同一账号在多台电脑装无为客户端，手机端可选择用哪台在线电脑执行/通讯，灵活切换。
>
> 路线决策：**A 路线 · 电脑端主动连云中转**（董事长拍板）。手机、电脑都不需公网 IP，最通用。

---

## 0. 核心约束：按需激活，绝不全员常连（董事长 2026-10-02 强调）

**WS 常驻连接是稀缺资源**——服务器连接数/端口有限，绝不能每台装了无为的电脑都无脑连 relay，那是巨大浪费，且大多数用户根本不用这个模式。

设计铁律：
1. **默认不连**。只有用户在**电脑端设置里主动开启**「允许手机端远程调用本机」，该电脑才建立 relay 常驻连接。没开 = 零连接、零负担、不占 relay 资源。
2. **订阅同步也要单独开关**。开启远程后，用户可**单独勾选**「把本机订阅版模型（Claude Code 订阅/Codex 订阅）同步给手机端」——
   - 勾了：手机端能看到并调用这台电脑的本地订阅渠道。
   - 不勾：只允许远程执行（走该机其他配置），本地订阅不外露、不同步。
3. **relay 服务容量 = 激活用户数**，不是全体用户数。这让端口/连接压力完全可控、可预估。
4. 激活是「每台电脑独立开关」：用户可以只在常用的那台开，其余不开。

> 落地影响：电脑端默认不含任何 relay 逻辑的运行开销；relay 服务按"活跃激活数"做容量规划即可，不必为全量用户预留连接。

## 1. 一句话架构

```
手机 App ──HTTPS/WSS──► 云中转(服务器 relay) ◄──WSS常驻── 电脑端无为客户端(多台)
                                                              └─ 本机 Claude Code 订阅(MINICC_OAUTH_TOKEN)
```

- **电脑端**：无为客户端启动后，用 WebSocket 常驻连到服务器 relay，**上报**：账号、设备 id、设备名、在线状态、本机可用渠道（含 Claude Code 订阅是否就位）。
- **手机端**：发消息前先选「用哪台在线电脑」；消息经 relay 转发到那台电脑；电脑用**本机的 Claude Code 订阅**跑 agent；流式结果经 relay 回传手机。
- **手机、电脑都只做出站连接**（都连服务器），不需要任何一端有公网 IP / 穿透。

与现有「无为托管」模式的关系：**并存，不替换**。
- 托管模式（现状）：手机 → agent 服务 → 无为网关 → 各模型，走托管币。
- 远程设备模式（新增）：手机 → relay → 电脑 → 电脑本机订阅渠道。
- 手机端模型选择器顶部多一个维度：**先选「执行位置」**（无为托管 / 我的某台电脑），再选该位置下可用的模型。

## 2. 为什么是 A 路线

| | A·电脑连云中转 | B·电脑开服务+内网穿透 | C·只做托管多设备 |
|---|---|---|---|
| 手机/电脑需公网IP | 都不需要 | 电脑需穿透 | 不需要 |
| 用到电脑Claude Code订阅 | ✅ | ✅ | ❌ |
| 多电脑切换 | ✅天然支持 | 勉强 | ✅ |
| 稳定性/安全性 | 高(统一走服务器鉴权) | 低(穿透易断、暴露面大) | 高 |
| 工作量 | 中大 | 中 | 小 |

A 的代价是要在服务器加一个 relay 常驻服务 + 电脑端加常驻连接，但一次铺好，③④一起解决，且安全（全程服务器侧鉴权、无裸露端口）。

## 3. 组件与改动点

### 3.1 服务器：新增 relay 服务（wuwei-relay）
- 技术：Node + `ws`（WebSocket），systemd 常驻，nginx 反代 `relay.wuweiai.io`（WSS，复用 acme.sh 证书套路）。
- 端口：避开 8790(gateway)/8791(agent)/3000(site)，用 **8792**。
- **容量 = 激活用户的在线电脑数**（不是全体用户）。因默认关、按需开，relay 只承载"主动激活了远程模式"的少数设备连接，端口/连接压力可控、可按活跃数线性扩容。
- 单账号可接受上限（如每账号最多 N 台在线设备）做保护，防滥用占连接。
- 职责：
  1. **设备注册表**（内存 + 可选落 Supabase 持久化）：`account_id → [device...]`，device = {deviceId, name, online, channels, lastSeen, connId}。
  2. **鉴权**：电脑端和手机端连入都要带 Supabase access_token，relay 校验（复用 agent 的 authUser 逻辑），只允许同账号的手机 ↔ 电脑互通。
  3. **路由转发**：手机发来 {targetDeviceId, sessionId, message, model} → 找到该电脑连接 → 透传；电脑回的流式分片 → 透传回对应手机连接。
  4. **掉线处理**：电脑断连 → 标记 offline、广播给该账号在线手机；手机发给已离线设备 → 立即回错误「设备不在线」。

### 3.2 电脑端（E:\git\wuwei）：新增「远程代理」模块（按需激活）
- **两个独立开关（都默认关）**，存本机配置（~/.wuwei 下）：
  - `remote.enabled`：允许手机端远程调用本机 → **开了才建 relay 常驻连接**，不开则该模块完全不运行、零开销。
  - `remote.shareSubscription`：把本机订阅版模型同步给手机端 → 仅在 enabled 时有意义；不开则上报的渠道清单里**剔除**本地订阅（claude-code-subscription / codex-subscription）。
- 新增 `src/remote/relay-client.ts`：
  - **仅当 remote.enabled=true** 才用 WSS 连 `relay.wuweiai.io`，带 access_token + deviceId（复用 `device-id.ts`）+ deviceName（os.hostname，可在设置自定义）。
  - 上报本机渠道清单：探测 `MINICC_OAUTH_TOKEN` 是否存在 → 标记 `claude-code-subscription` 可用；同理 Codex 订阅、API key。
    **但若 remote.shareSubscription=false，则上报清单里不含本地订阅渠道**（只报允许远程跑的非订阅渠道，或干脆只报"在线可执行"不报具体订阅）。
  - 收到 relay 转发的「执行请求」→ 复用现有 agent loop（`src/agent/loop.ts` + `provider.ts`）跑，用**本机 config**（即本机的 Claude Code 订阅）→ 把 text/tool/done/error 事件回传 relay。
  - 心跳保活、断线重连（指数退避）。
- **复用而非重写**：执行内核就是桌面端现成的 agent loop，远程模块只是「把输入从 relay 喂进去，把输出发回 relay」的适配层。

### 3.3 手机端（E:\git\wuwei-mobile）：执行位置选择 + 远程通道
- **API 层**：新增 `src/api/devices.ts` → `GET /devices`（经 relay 或 agent 拿当前账号的在线设备列表）。
- **对话发送**：当选择的执行位置是「某台电脑」时，`/chat` 改走 relay 的 WSS 通道（而非现在的 agent SSE）；payload 带 `targetDeviceId`。
- **UI**：
  - 模型选择器升级为**三层**或在顶部加「执行位置」切换：
    - 执行位置：`无为托管`（默认）/ `💻 我的MacBook`（在线）/ `💻 公司台式机`（离线·置灰）
    - 选「无为托管」→ 走现有托管模型两级列表（已完成）。
    - 选某台电脑 → 列该电脑可用渠道（Claude Code 订阅 / 其本机配置的模型）。
  - 离线设备置灰不可选 + 「不在线」提示。
  - 对话页顶部显示当前执行位置小标（如「💻 MacBook · Claude Code」）。

### 3.4 数据流（手机用电脑的 Claude Code 订阅发一条消息）
```
1. 手机: 选执行位置=MacBook, 模型=Claude Code订阅
2. 手机 → WSS relay: {type:chat, targetDeviceId:MacBook, sessionId, text:"..."}
3. relay: 校验token/同账号/目标在线 → 转发给 MacBook 的电脑端连接
4. 电脑端: 用本机 config(oauth订阅) 跑 agent loop
5. 电脑端 → relay: 流式 {type:delta,text} / {type:tool} / {type:done}
6. relay → 手机: 原样透传 → 手机逐字渲染
7. 会话 messages 存哪：沿用 wuwei_sessions(Supabase)，由电脑端或relay在done时写回
```

## 4. 分期实施（建议）

- **M1 · relay 骨架 + 在线状态（对应需求④的基础）**
  服务器起 wuwei-relay(ws, 8792) + nginx `relay.wuweiai.io`；电脑端常驻连接 + 上报在线/设备名；手机端 `GET /devices` + 执行位置选择器(只显示在线列表，先不路由执行)。
  产出：手机能看到「我有哪几台电脑在线」。

- **M2 · 远程执行打通（③④核心）**
  relay 路由转发；电脑端收请求→跑本机 agent→回流式；手机端 /chat 走 relay。
  产出：手机选某台电脑 + Claude Code 订阅，能真发消息、看流式回复。

- **M3 · 健壮性**
  断线重连、离线兜底、额度回显（Claude 订阅的 5h/7d 额度头，provider.ts 已能解析）、安全加固（连接鉴权、同账号隔离、消息大小限制）。

## 5. 风险与注意
- **安全是第一位**：relay 必须严格校验「手机和电脑是同一账号」，否则会出现 A 用户的手机连到 B 用户电脑的订阅——这是红线。连接入场即验 token，路由前再验账号一致。
- **电脑端常驻连接的功耗/打扰**：默认开但给开关；连接只在客户端运行时存在，关客户端即离线（符合直觉）。
- **Claude Code 订阅额度是账号级共享池**：手机远程用会消耗你电脑订阅的 5h/7d 额度（和你本机用同一个池），需在 UI 明示额度，避免手机端跑爆影响电脑端。
- **会话一致性**：远程模式产生的会话也存 wuwei_sessions，保证手机/桌面都能看到历史。
- **不碰现有托管链路**：远程是新增通道，托管模式原样保留，互不影响。
